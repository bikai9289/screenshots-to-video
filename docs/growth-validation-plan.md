# Screenshots to Video 增长验证方案

日期：2026-11-03。状态：执行计划，所有实验均未开始，不代表已有流量或转化结果。

配套文档：[开发方案](./development-plan.md)、[上线验收清单](./launch-checklist.md)。

## 1. 目标与执行边界

验证目标用户如何寻找截图转视频工具、搜索和 AI 如何发现本站，以及付费路径是否成立。补齐用户提供的 13 项行动中的增长实验部分。

- 产品定位保持付费，不提供免费生成额度；公开示例可浏览。
- 第一版 UI 是视觉基准。内容补充优先用短句、截图、动效和折叠 FAQ，不堆积大面积文字。
- 社群摘录是用户提供的经验线索，未独立核验原帖、日期或说话人；本方案不将其包装成已验证的普遍规律。
- 先完成真实产品能力与上线验收，再开始流量和付费效果实验。
- 本文只制定方案，不授权自动发帖、购买外链、改价或发布内容；执行时遵循用户实际授权。
- 不承诺搜索排名、AI 推荐或转化率。模型回答是观察证据，不能单独证明实际用户需求。

## 3. 关键词与零外链观察

### 3.1 准备

- [ ] 首页候选核心词为 `screenshots to video`，记录选择依据；不因精确匹配域名就认定有需求或低竞争。
- [ ] 将搜索结果页面类型、用户意图、相关竞品和已查数据记录在同一批次，注明地区、语言、日期、来源及工具口径。
- [ ] 若查询搜索量或难度，保留本轮工具返回；历史数值标明时间，不能冒充当前数据。数据缺失写未知。
- [ ] 完成生产 SSR、公网访问、付费生成与来源埋点验收，排除模板遗留内容。
- [ ] 不因观察实验再次注册域名；当前域名已确定。

### 3.2 D0–D7 规则

D0 为完成上线验收并开启来源记录的日期，统一使用 Asia/Shanghai。记录 D0 基线，在 D1–D7 每日固定时段读取前一个完整自然日；D7 结束后汇总七个完整自然日。

- 不主动购买、交换、提交目录或群发获取外链；自然产生的链接如实记录。
- 不投广告，不主动在社群推广。若必须推广，标记日期、渠道和 UTM，单独分析；该窗口不能再称为纯零外链自然流量实验。
- 可以按正常流程提交 sitemap；记录提交和首次收录日期。
- 本团队的浏览、自动测试和指定网址 AI 抓取是测试访问，不计入真实用户流量；以测试标识、专用链接或已知时间段辅助排除，不只依赖 IP。
- 安全、支付、服务可用性和事实错误随时修复；其他文案、价格、页面结构尽量固定。任何修改写入变更记录。
- 观察系统故障、日志缺失或供应商不可用时，记录失效时段，恢复后另建观察窗口，不用坏数据判断需求。

每日记录字段：日期、页面版本、抓取/收录状态、搜索曝光、搜索点击、有效访问、已知 AI 来源、direct/未知、制作点击、付费墙触达、checkout、已确认付款、生成成功、测试流量排除方式、异常与变更。

### 3.3 观察后的决策

| 现象 | 下一步 | 不能直接下的结论 |
| --- | --- | --- |
| 未收录或抓取失败 | 先修复可访问性、索引配置和内容问题，再开窗口 | 不能说关键词没需求 |
| 已收录但无曝光 | 检查时间、意图、查询覆盖和竞争证据，决定是否延长观察 | 不能仅凭七天决定换词 |
| 有曝光但点击少 | 对照查询检查 Title、描述和页面匹配 | 不能只怪外链不足 |
| 有有效访问但不制作 | 检查入口、成片证据、用途和操作阻力 | 不能据此认定价格必然过高 |
| 有制作意愿但不购买 | 检查付款故障、报价理解、套餐与信任信息 | 不能未经对照就改为免费 |
| 有自然访问与真实使用/付款 | 保留方向，提出下一轮内容或外链实验 | 不能证明竞争一定低或外链带来增量 |

外链放量前单独制定渠道、成本、授权和衡量方式，不与首轮文案、套餐实验同时变更多个变量。

## 4. 多模型反推用户问题

在 ChatGPT、Claude、Gemini 中分别进行一次无品牌提问。只使用当前可访问的产品，记录产品、模型（若显示）、联网状态、语言、日期；不可访问的标为未测试。

统一提示词：

> 假如你是 SaaS 创始人或产品营销人员，手里有应用截图，想制作产品演示、功能更新或发布视频，你会怎样向 AI 寻找工具？请给出 10 个自然英文问题，覆盖比较、付费、输入限制、编辑、导出和隐私。不要推荐品牌，不要编造搜索量。每个问题注明用户目标。

合并结果时按需求去重，保留原始问题与来源。首批选 10–15 个问题，至少包含产品发布、功能更新、制作方式、收费、导出和隐私。没有实测数据时不把模型生成的问题称为真实高频搜索。

问题库字段：`question_id`、英文问题、中文意图、用户角色、决策阶段、来源模型、是否暗示不存在的能力、对应页面/FAQ、优先级。

有真实 Search Console 查询、客服问题或访谈材料后另加来源，不覆盖原始模型候选。

## 5. 逐问测试与引用记录

对首批问题逐个使用独立新会话，不提供本站名字，不粘贴前一题答案。各模型记录其实际可用的联网能力；没有联网的回答只能作为文案线索。

每题先运行一轮；需要验证稳定性时，在另一个日期按相同条件复测。样本少时只列观察次数，不声称有统计显著性。

记录表字段：

| 字段 | 记录要求 |
| --- | --- |
| `run_id / question_id` | 唯一测试批次和题目 |
| 日期、模型、地区/语言、联网设置 | 只记实际可见信息，未知项标未知 |
| 原始提问与回答 | 保留完整证据，分享前检查私人信息 |
| 可见子查询/检索过程 | 只记录产品展示的搜索过程，不推测模型隐藏推理 |
| 引用 URL、标题、推荐品牌 | 按实际链接记录；没有引用写未提供 |
| 本站是否被提及/引用 | 提及和引用分开，记录对应句子 |
| 实际读取还是摘要 | 无法判断写未知，不凭引用存在就声称实时读取 |
| 推荐理由与信息缺口 | 区分模型说法与页面可验证事实 |
| 运行失败 | 无网络、访问被拒、超时或没有回答分别记录 |

指标只描述这个问题集：本站提及次数/有效回答数、引用次数/有效联网回答数。分母、重复测试和失败数必须公开，不能当作全网 AI 市占率。

## 6. 从问题与引用生成内容任务

将第 5 节记录交回 AI 分析，要求依据记录输出，不编造新数据：

> 根据这些问题、回答和引用页面，找出本站尚未回答的需求。每个内容任务注明 question_id、证据、用户目标、推荐页面类型、核心内容、所需真实图片/成片、内链入口和适合的发布渠道。不要为了铺词批量生成重复页面，不要建议未实现的功能。

页面承接规则：

| 需求 | 承接位置 | 控制文字量 |
| --- | --- | --- |
| 核心用途与成片效果 | 首页首屏、案例 Tabs | 用现有位置的一句说明和主要媒体，不增大段正文 |
| 购买前规则 | 折叠 FAQ、定价和政策页 | FAQ 短答，详细规则链接出去 |
| 真实制作步骤 | 配图教程 | 一步一张操作图，必要说明分段 |
| 不同场景 | 独立场景页，仅在需求和素材独立时创建 | 展示对应真实示例，避免换标题复制首页 |
| 产品比较 | 有依据的对比页或文章 | 列出已核验差异与核验日期，不杜撰竞品缺点 |

发布渠道先形成建议清单：站内教程、产品文档、与受众相关的社区或演示渠道。每条写明受众、内容形式、渠道规则、链接目的和来源标记；未获发帖授权前不发布。

若继续零外链实验，外部渠道发布排到观察结束之后。发布后进入新的观察批次，不与零外链数据混算。

任务记录：内容 ID、证据题目、目标页、图片/视频需求、拟稿、事实核验、内链、渠道、负责人、状态、发布 URL、复测结果。没有素材或功能证据的任务先阻塞，不用虚构内容补齐。

## 7. 角色互换与带品牌对照

先完成第 5 节的无品牌测试，再另开会话执行带品牌诊断，不能在无品牌测试中途加入本站来提高“自然推荐率”。

角色提示词：

> 假如你是第一次发布 SaaS 的独立开发者，只有几张界面截图，不想录屏，愿意为合适的工具付费，你会如何提问、比较和决定购买？请说明你需要看到哪些证据。

带品牌提示词：

> 听说 screenshotstovideo.com 可以用截图制作产品视频，请访问它，并与当前可核验的同类工具比较。哪些需求适合它，哪些信息仍不足？不要把宣传文案当作已测试功能。

保留两类实验标记 `unbranded` / `brand_prompted`。只根据事实缺口和反复出现的用户阻力提出修改，不因一句推荐倾向重做第一版 UI。

## 8. 竞品对标与推荐原因

首个候选是本会话此前选定的 Tellcut 截图转视频页面；DemoScreen 可作案例和计费表达参考。实施时重新核对官方页面，不把会话中的价格、模型、功能或效果当作当前事实。

- [ ] 记录候选站公开页面、日期、页面标题、核心用途、首屏说明、案例证据、FAQ、价格路径和付费限制。
- [ ] 向实际联网模型询问推荐该竞品的具体原因，要求链接及页面证据；无法访问的写未知。
- [ ] 把原因分为功能适配、效果证据、规则清晰度、使用体验和外部知名度，避免把所有优势都归因于文案。
- [ ] 对照本站逐项标记已有、表达不足、功能缺失、无法核实。
- [ ] 只补真实缺口；功能缺失形成开发任务，不能先在页面宣称支持。

学习信息架构和表达清晰度，不复制品牌、专有素材、客户评价、示例成片和整段文案。任何新增模块都先判断能否在第一版现有模块中承接。

## 9. 付费墙与套餐实验

固定约束：无免费生成；收费前明确价格、计费单位和失败处理；购买、扣费与资格校验以服务端为准。

用户提供的候选如下，仅用于成本评估，不是已批准商品：

| 候选 | 价格（USD） | 次数 | 需要先定义 |
| --- | --- | --- | --- |
| 单次 | 9.90 | 1 | 什么算一次、有效期、允许时长和输出规格 |
| 小包 | 19.90 | 3 | 重试、修改和多比例导出是否额外收费 |
| 多次包 | 29.90 | 5 | 有效期、退款及剩余次数处理 |

实施前核算单次渲染、存储、流量、支付费用、失败和重试成本；确认退款、税费展示和货币。不能用原模板订阅积分直接冒充上述按次产品。

实验顺序：

1. 先验证现有付费路径能正常展示、支付和生成，建立基线。
2. 确认候选商品规则和成本后取得实际改价授权，同步目录、UI、checkout、FAQ 与条款。
3. 一轮只测试一个明确变量，如套餐呈现或价格；保持受众、页面、功能与归因记录尽量一致。
4. 流量足够时按用户稳定分组，避免同一用户反复看到不同价格；流量不足时按时间批次观察并注明季节、渠道和样本差异，不称为严格 A/B 结论。
5. 预先记录观察窗口、最低样本要求和可承受的退款/成本阈值。样本要求由基线与目标差异计算；无基线先做探索，不用一个武断人数声称结果可靠。

指标分别记录：有效访问到已确认付款、付费墙到 checkout、checkout 到付款、净收入、退款、生成成功、付费后任务失败和单次实际成本。明确去重、时间窗口、用户与订单口径。

社群“约 8% 转化率”不作为本站验收目标；其来源口径、分母、样本和观察期未核实，不能写进公开承诺或收入预测。

付款故障、重复收费、未授权生成或成本失控出现时停止分流并修复，保留既有购买权益；价格实验不能追溯更改已购商品。

## 10. 来源归因与复测

复用现有 `src/config/events.ts`、`src/lib/track.ts`、`src/routes/api/events.ts` 及现有分析系统，先审查能力再决定是否扩展；不要另建重复事件流水。

来源至少分为：可识别搜索、可识别 AI 引荐、已标记推广、direct/未知、内部测试。细分主机以实际 referrer 为准，规则变动留版本。

- 记录入口路径、referrer 主机和白名单 UTM；首次来源与本次会话来源分开保存，明确保留期限及同意要求。
- 缺失 referrer 的访问保持未知，不自动归为 GPT；用户自愿来源回答单独存为自报信息。
- 流量标记不作为鉴权依据。浏览器不上报可信付款或积分结果，以服务端确认的订单和任务为准。
- 新浏览器事件先注册 `client: true`，增加双语 timeline 标签；来源等 detail 遵守项目的扁平结构和长度限制。
- 不把来源事件塞进业务服务跨模块调用；在 API 层协调，也不重复记录已能从订单或任务行取得的事实。
- 数据采集失败不影响购买和生成；不记录截图、完整敏感 URL、密钥或支付信息。

每轮只复测本轮调整对应的问题组，保留旧记录。定期汇总未知来源比例、测试流量排除情况、漏斗缺失环节和失败任务，避免把埋点故障看成市场结果。

## 11. 执行清单与产物

实测开始后在 `docs/growth-validation/` 按批次建目录，命名为 `YYYY-MM-DD-实验主题`。本文不提前创建空结果或伪造基线。

- [ ] G1：记录核心词依据与上线基线，检查正式产品及归因是否可用。
- [ ] G2：合并多模型问题库，首批选取 10–15 个问题。
- [ ] G3：执行无品牌逐问测试，记录引用 URL、标题和可见检索行为。
- [ ] G4：完成 GPT 网址抓取、直接推荐诊断、角色互换与竞品对照，分类保存。
- [ ] G5：以真实缺口生成内容计划和图片需求；保持第一版 UI 的留白与短文案。
- [ ] G6：在不主动建设外链和不推广的窗口内观察七个完整自然日，排除团队测试访问。
- [ ] G7：汇总数据，决定修复、延长观察、保持方向或开展下一轮；记录理由和替代解释。
- [ ] G8：完成成本与商品规则评估，获授权后执行套餐实验。
- [ ] G9：内容或渠道获发布授权后执行，再开独立观察批次。

每个批次产物包含：实验目标与变量、来源材料、问题库、原始回答、引用页面清单、每日观测、变更日志、费用、结论及下一步。公开分享前移除账号、私有会话和个人数据。

完成标准是能从记录追溯“做了什么、看到了什么、因此决定什么”。尚未访问、未运行或无法核验的项目仍标为未验证；不以文档完成代替增长验证完成。
